# 技術架構與原型 BOM

> 對象：自己動手做第 0 階段原型的人（開發主力用 AI）。價格是 2026 年台灣零售行情的粗估，要以實際報價為準。

## 1. 系統架構

```
[地墊感測層] --有線--> [Alishan Sense 模組艙] --Sub-GHz/BLE--> [大樓閘道器] --4G/網路線--> [Alishan Cloud]
  壓電底座條               邊框端部・灌膠密封                     插電・一棟一台                 門檻、預測
  荷重元 ×4（新案）        MCU＋RF＋鋰亞電池                                                   工單、報表
  溫濕度／積水電極                                                                              │
  ToF 積砂高度（改裝）                                                                           ├─> LINE 官方帳號（Messaging API）
                                                                                                ├─> 管理儀表板
                                                                                                └─> ESG／WELL 月報
```

第 0 階段先簡化：ESP32 同時當模組和閘道器，直接連 Wi-Fi 呼叫 LINE API。

## 2. 感測方案比較

| 方案 | 量到什麼 | 耗電 | 放在哪 | 評估 |
|---|---|---|---|---|
| FSR402（原提案） | 單點壓力 | 要一直供電 | 只有 12.7 mm | ✗ 蓋不住 30 mm × 數公尺的鋁條 |
| **壓電感測底座條**（壓電線／PVDF 薄膜） | 踩踏事件、次數 | **被踩到時自己產生電壓，可以直接喚醒 MCU** | 取代 PVC 避震底座 | ✓ 主力：計數＋喚醒 |
| **荷重元 ×4＋HX711** | 總重量 → 積砂重量 | HX711 約 1.5 mA，**不能一直開** | 凹槽四角（新案多挖 5 mm） | ✓ 每小時量一次，只在沒人踩時量 |
| **ToF（VL53L1X）** | 凹槽積砂高度 | 量一次約 20 mA × 50 ms | 邊框內側角落，沿著凹槽看 | ✓ 改裝案用；新案用來交叉驗證 |
| 溫濕度（SHT40）＋積水電極 | 濕度、積水 | 很低 | 凹槽邊 | ✓ 用在滑倒風險和異味 |
| 毫米波雷達（人流） | 人數、方向 | 高 | 門框上 | △ 之後做數據產品時再評估 |

**關鍵工程判斷**：只用荷重元來數步數，HX711 必須持續取樣，大約 36 mAh／天，一顆 AA 鋰亞電池（約 2,600 mAh）只能撐兩個多月。所以要分工：**壓電負責偵測踩踏並喚醒，荷重只量基線**。

## 3. 功耗預算（量產模組目標）

| 項目 | 估算 |
|---|---|
| 深度睡眠 | 約 5 µA × 24 h ≈ 0.12 mAh／天 |
| 壓電喚醒計數（2,000 步／天 × 3 ms × 5 mA） | 約 0.01 mAh／天 |
| 荷重基線（24 次 × 0.5 s × 2 mA） | 約 0.007 mAh／天 |
| ToF／溫濕度（24 次） | 約 0.01 mAh／天 |
| 無線批次上傳（96 次 × 30 ms × 15 mA） | 約 0.012 mAh／天 |
| **合計** | 約 0.16 mAh／天。加上自放電和峰值的保守係數，**目標 3–5 年** |

電池：ER14505（AA 鋰亞硫醯氯，3.6 V、約 2,600 mAh），跟胎壓計的做法一樣，封在模組內，到期整顆模組更換。

## 5. 原型步驟（約 4 週）

1. **第 1 週：訊號與結構**
   - 把 ES302 樣品放進一個 2 cm 深的木框當作凹槽，四角墊荷重元。
   - 把 ESP32 放進防水盒，擺在邊框位置，測 Wi-Fi／BLE 的 RSSI：蓋上鋁框和不蓋各測一次。
2. **第 2 週：感測**
   - 壓電：踩踏喚醒 → 計數寫進 RTC 記憶體 → 回到睡眠。拿手動計數器比對 200 步。
   - 荷重：在沒人踩的時候取 10 次平均值；倒入 50 g、100 g、200 g 的砂，看讀數的解析度。
3. **第 3 週：雲端與 LINE**
   - 建 LINE 官方帳號 → 開啟 Messaging API → 取得 Channel access token。
   - 先用最簡單的後端（Cloudflare Workers、Google Apps Script 或 Firebase 都可以）接收 ESP32 的 HTTPS POST，達到門檻就呼叫 `POST https://api.line.me/v2/bot/message/push`。
   - Webhook 處理「今日狀態」這類查詢，用 reply API 回覆（**回覆訊息不計入推播額度**）。
4. **第 4 週：展示**
   - 在公司門口實際放 1 週，錄一段「踩上去 → 手機收到 LINE」的影片。
   - 把量到的每人帶入砂量、濕度曲線填回模擬參數（`web/src/sim/engine.js` 的 `SIM_CONFIG`）。

**要進第 1 階段的條件**：人次誤差 < 5%；積砂可以量到 50 g 的變化；蓋上鋁框後 RSSI 還能穩定連線。

## 6. 韌體架構（給 AI 寫程式時的規格）

```
開機 → 初始化 → 設定喚醒來源：壓電 GPIO（ext0/ext1）＋計時器（15 分鐘）
每次醒來：
  if 喚醒原因 == 壓電:  step_count++（RTC 記憶體）；短暫防彈跳 300 ms；回到睡眠
  if 喚醒原因 == 計時器:
     if 整點 且 最近 60 秒沒有踩踏: 開 HX711 → 取 10 次平均 → 扣掉空載基準 → debris_g
     量溫濕度、ToF
     組成 JSON {id, t, steps, debris_g, rh, temp, tof_mm, batt_mv}
     連線 → HTTPS POST → 成功才把 step_count 歸零
  回到深度睡眠
```

雲端門檻（跟模擬引擎一致）：積砂 ≥ 70% 自動開清潔工單；濕度 ≥ 45 開濕滑警示、≤ 30 自動結案；毯條壽命 ≤ 10% 排程更換；23:00–06:00 有人踩就發入侵警報。

## 7. 第 1 階段：跟親戚胎壓計工廠合作的重點

| 題目 | 要談的內容 |
|---|---|
| 模組艙 | 尺寸大約 130 × 34 × 26 mm，嵌在實心鋁邊框端部；上蓋用 PC／PA 當天線窗 |
| 密封 | 灌膠（環氧樹脂或聚氨酯）做到 IP68；要能承受拖地的水和中性清潔劑 |
| 無線 | Sub-GHz（例如 433／915 MHz，要確認 NCC 規範）或 BLE 長距離模式；閘道器放在大廳 |
| 電池 | ER14505 焊片式；電池壽命的驗證方法 |
| 量產 | 治具、校正流程、出廠測試、品質追溯 |
| 法規 | NCC 低功率射頻型式認證（量產前一定要做） |

## 8. 測試清單

- [ ] 蓋上鋁框後的 RSSI（晴天／雨天）
- [ ] 灌膠模組浸水 1 m、30 分鐘（IP67），以及長時間浸泡
- [ ] 高壓沖洗、中性清潔劑浸泡
- [ ] 荷重：推車、輪椅、板車通過時（ES302 規格就有列這些）
- [ ] 平均電流實測 → 推算電池壽命
- [ ] 積砂量：人工秤重和系統讀數比對（至少 10 次）
- [ ] LINE：推播與回覆的延遲、每月推播則數
